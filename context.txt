They are likely not calling elevation APIs per point.

They probably do this:

Pre-download DEM raster tiles
USGS/NED, SRTM, LiDAR, Copernicus DEM, etc. TowerCoverage says its maps use “topography and land cover data,” and mentions USGS/LiDAR datasets.
Load all tiles covering the radius once
Example: GeoTIFF / Cloud-Optimized GeoTIFF / MBTiles / PostGIS raster.
Sample the raster locally
For each azimuth/range pixel, they read elevation from the in-memory raster grid, not from Google/OpenTopoData.
Run RF/viewshed propagation on the grid
Usually Longley-Rice/ITM, LOS, Fresnel, clutter/land-cover loss, or similar. TowerCoverage advertises RF propagation using terrain and land-cover data.
Render result as raster/vector overlay
The green/red areas are computed coverage pixels, then displayed over satellite tiles.

For your own implementation, the scalable pattern is:

tower lat/lon + radius
→ find intersecting DEM tiles
→ read raster window once
→ reproject to local metric grid
→ compute terrain profile / viewshed / RF loss
→ output PNG tiles or polygons

Use COG GeoTIFFs + GDAL/rasterio. Avoid elevation APIs except for one-off point lookups. A 30 km radius at 30 m resolution is only about 3 million samples, which is normal for local raster processing.

If your question is specifically:

"How could they avoid thousands of elevation API calls?"

The answer is straightforward: commercial RF systems almost never depend on per-point Google/OpenTopoData requests during propagation. They keep terrain locally and query raster files directly. Once terrain is local, billions of elevation samples are orders of magnitude faster than billions of HTTP requests.

Meaningful reverse-engineering from their public docs:

Their likely engine path

coverage request
→ choose rendering quality
→ load local terrain + clutter datasets
→ for each sampled receiver point:
     FSPL(distance, frequency)
     terrain obstruction / clearance
     if NLOS: ITM point-to-point obstruction loss
     if LOS: two-ray ground-reflection model
     earth curvature + refraction
     first-Fresnel-zone intersection with clutter
     vegetation / urban penetration loss
→ color output by performance level
→ save raster coverage image / overlay
→ merge into multi-map / expose via iframe/API

Evidence: TowerCoverage says FSPL is computed for every calculation, terrain is added as obstruction/clearance, NLOS uses Irregular Terrain Model in point-to-point mode, LOS uses two-ray, and coverage is produced by computing millions of point-to-point links.

The “1 meter” part is probably dataset availability and selected render mode, not “every 30 km map is always solved as a 2.8B-cell dense raster.” Their own rendering-quality table says:

ULTRA = highest available clutter and elevation data
VERY HIGH = up to 1/9 arc-second clutter where available + highest elevation
HIGH = up to 1/9 arc-second clutter/elevation
MEDIUM = 1/3 arc-second clutter + 1/9 elevation
LOW = 1/3 arc-second
VERY LOW = 1 arc-second

So the real trick is likely:

“1 m source/clutter/elevation where available”
+
“millions of sampled links”
+
“render-quality-dependent sampling”
+
“cached generated overlays”

not:

Google/OpenTopoData call per point

Their docs also list local/raw sources: USGS NED, SRTM, Alaska NED, CDED/CANVEC/ASTER/Viewfinder Panoramas for elevation; NLCD, Canada landcover, Corine, GlobCover for land cover.

Most revealing detail: their API is old SOAP/HTTP endpoints like towercoverage.asmx, with explicit API-call limits, while coverage counts and “unlimited reprocessing” are product features. That points to a server-side batch/render queue, not browser-side live computation.
